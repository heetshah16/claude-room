# Orchestrator extension: claude-room as something you install

**Status:** approved design, not yet implemented
**Date:** 2026-09-05

## Problem

Everything in this repo works, and almost nobody can run it. Getting to a
working room today means: clone, `npm install`, start the server, read a
token out of stderr, run `room-admin seat add`, launch a seat in a second
terminal, open a browser. That is a demo, not a product.

This is a **packaging** problem first. The pivot is: install one thing, get
a chat window, and have the workers managed for you. The orchestrating
Claude answers in a proper chat surface — streaming prose, tool calls,
diffs — rather than a terminal, and cheap OpenCode workers pick up the
mechanical work with their activity visible beside it.

Multiplayer does not go away. Solo is the default; the shared room stays
available for when a teammate should join.

## What was verified before designing

Against the real binaries on this machine, not from documentation:

| Fact | Evidence |
|---|---|
| **One `claude` process serves many turns** | `--print --input-format stream-json --output-format stream-json`: two prompts, one `session_id`, and it recalled a fact from turn 1 in turn 2 |
| The stream is rich enough to render a real chat | `system/init` (session_id, tool list), `system/thinking_tokens` (live deltas), `assistant` (content blocks), `result` (session_id, `total_cost_usd`) |
| `--append-system-prompt` exists | used in the probe to constrain the orchestrator's voice |
| **`--bare` cannot be used** | it "never reads OAuth or keychain" and requires `ANTHROPIC_API_KEY`; the whole point is reusing the user's existing subscription login |
| A spawned session inherits ambient config | the probe's session fired a `SessionStart` hook from the user's global setup and injected unrelated context |
| The delegation path works end to end | MCP `delegate` → real OpenCode seat → real `room_reply` → `delegation-result`, with the worker running the command named in `spec.tests` |

Two consequences shape the design:

1. **The orchestrator is a long-lived process, not a series of one-shots.**
   That is what makes the chat feel like a chat.
2. **The orchestrator does not need to be the room's `@claude` channel.**
   Because its output goes to our own UI rather than through `room_reply`,
   it needs exactly one thing from the room: the `delegate` tool. That
   collapses a chicken-and-egg problem described under "Rejected
   alternatives" and removes the room's hook-settings dance entirely.

## Design

### 1. Repo layout

```
src/            the room — unchanged, still zero runtime dependencies
scripts/        launchers — unchanged
extension/      the VS Code extension: its own package.json, its own deps
```

The room stays dependency-free. The extension is a separate package with
dev-only dependencies (`@types/vscode`, `esbuild`, `typescript`) and
bundles to a single file. Nothing in `src/` may import from `extension/`.

### 2. Process model

The extension supervises three kinds of process:

```
VS Code extension host
  ├─ room server        node src/server.mjs   ROOM_STANDALONE=1, known port
  ├─ orchestrator       claude --print --input-format stream-json ...
  │                       └─ MCP stdio child: src/orchestrator-bridge.mjs
  └─ worker(s)          node scripts/room-opencode-seat.mjs
                          └─ opencode serve (loopback)
                          └─ MCP stdio child: src/seat.mjs (reply-only)
```

The extension picks every port by binding `127.0.0.1:0` and releasing, and
owns the lifecycle of everything it spawns.

**`Supervisor`** (`extension/src/supervisor.ts`) is the one place that
starts, watches and stops a child. It must:

- treat a child exiting as an event to surface, never to ignore — the room
  dying silently while the chat still accepts input is the worst failure
  this design can have
- kill process **trees**, not processes. On Windows `spawnPortable` routes
  a `.cmd` shim through `cmd.exe`, so killing the child orphans the real
  server. This is not hypothetical: it was observed twice during the
  OpenCode work, leaving `opencode serve` holding a worktree and a port.
- restart with backoff, and give up loudly rather than looping
- shut everything down on deactivate, in reverse dependency order

### 3. The orchestrator session

`extension/src/orchestrator.ts` owns one `claude` process for the lifetime
of the chat.

```
claude --print
       --input-format stream-json --output-format stream-json --verbose
       --session-id <uuid generated by us>
       --append-system-prompt <orchestrator instructions>
       --mcp-config <path to a file naming src/orchestrator-bridge.mjs>
       --add-dir <workspace root>
```

A turn is one JSON line written to stdin:
`{"type":"user","message":{"role":"user","content":[{"type":"text","text":"..."}]}}`

Events are parsed line-by-line off stdout and forwarded to the webview:

| event | rendered as |
|---|---|
| `system/init` | session established; capture `session_id` for resume |
| `system/thinking_tokens` | a live "thinking" indicator with a token count |
| `assistant` | prose blocks appended; `tool_use` blocks as collapsible cards |
| `user` (tool results) | folded into the card that issued the call |
| `result` | turn complete; record `total_cost_usd` |

**Auth and ambient config.** We deliberately do *not* isolate
`CLAUDE_CONFIG_DIR`: the user's login is the entire reason this is
pleasant to install, and `--bare` would forfeit it. The cost is that the
orchestrator inherits the user's hooks and CLAUDE.md discovery. That is
mostly desirable — a project's CLAUDE.md should apply — but it means our
orchestrator instructions arrive via `--append-system-prompt` and must be
written to survive alongside whatever else the user has configured, not
assume a blank slate.

**Crash recovery.** The `session_id` is ours, generated before launch, so
a died-and-restarted orchestrator resumes the same conversation with
`--resume <id>` rather than losing the thread.

### 4. `src/orchestrator-bridge.mjs` — the only new room-side code

A thin stdio MCP server, the mirror of `src/seat.mjs`. It exposes
`delegate` (and `room_decision`) to the orchestrator and forwards each
call to the room over HTTP. It holds no state and no feed: the
orchestrator does not receive room events, because its conversation lives
in our UI, not in the room's transcript.

This requires one new room route: **`POST /api/delegate`**, owner-
authenticated, which calls the existing `delegator.delegate(...)` and
returns its `{ok, id, errors}` verbatim. The MCP tool schema, the
validation, the authorisation gate and the result path all already exist
and are unchanged.

The delegation **result** does not come back through the bridge. The
extension holds one SSE subscription to the room's `/events` (§6) and
routes what it sees: worker activity to the workers panel, and a completed
delegation into the orchestrator's conversation as a **new user-role
turn** — literally another line on its stdin, tagged so the orchestrator
can tell a worker's report from something the human typed. That is the
same shape a person relaying the result would take, which is why no new
protocol is needed for it.

The extension authenticates that subscription with the owner token. It
owns `ROOM_STATE_DIR`, so it reads the token from the room's own state
rather than scraping it from stderr the way an operator does today.

### 5. Chat webview

`extension/src/chat/` renders the orchestrator stream. It is a fresh
webview rather than a reuse of `src/ui.mjs`: that file renders the room's
*message* model, and the orchestrator's model is a *stream*. Reusing it
would mean bending both.

Requirements: streaming text that appends without reflowing the scroll
position, tool calls as collapsible cards showing input and result, a
visible thinking indicator, VS Code theme variables so it matches the
editor, and `textContent` for every model-supplied string — the same rule
`src/ui.mjs` states, for the same reason.

### 6. Workers panel

The extension opens **one** SSE subscription to the room's `/events` and
fans it out; `extension/src/workers.ts` is one consumer of that stream,
the orchestrator's result-relay (§4) the other. One subscription rather
than two keeps a single ordering of room events, so a worker's reply
cannot reach the orchestrator before the panel has shown the work.

It renders, per worker: handle, model,
current task, tool calls as they happen, the final reply, and **the
turn deadline counting down**. That last one matters: a free model that
stalls is invisible in a GUI in a way it is not in a terminal, and two of
six probe turns stalled.

Nothing new is needed room-side — the activity feed already publishes
this.

### 7. Installer

`extension/src/install.ts` detects `claude` and `opencode` using the same
PATH/PATHEXT resolution as `src/spawn.mjs` (which already handles the
Windows `.cmd` case). If either is missing, it shows exactly what will be
installed and where, and installs only on confirmation. Never silent: a
global npm install is precisely the kind of thing that should not happen
behind someone's back.

### 8. Solo and room modes

Solo is the default and needs no configuration: the room runs on loopback
with a single owner member, and no browser is involved.

"Share this room" flips `ROOM_HOST` to the tailnet address and surfaces
the join URL. Everything that makes sharing legitimate — per-seat
credentials, cost attribution, address policy — is already built and
untouched.

**The rendering asymmetry, stated plainly.** The orchestrator streams to
one local UI; seats speak in room messages that persist. A second human in
a shared room therefore sees the orchestrator's *replies* but not its
live stream. That is the correct trade-off — a stream is a local view, a
message is the record — but it means the orchestrator must be prompted to
say what it decided, not merely think it. The `--append-system-prompt`
carries that instruction.

## Rejected alternatives

**Orchestrator as the room's `@claude` channel** (the existing topology,
where Claude Code spawns the room as its MCP child). Rejected because it
inverts control: the extension could not then choose the room's port,
observe its health, or restart it independently, and the room's hook
settings file must exist before Claude Code starts while being written
only once the room is listening. Making the room standalone and giving the
orchestrator a thin bridge removes all of it.

**Reusing `src/ui.mjs` as the chat.** Rejected: message model vs stream
model, as above. It stays the browser client for shared rooms.

## Build order

Each stage leaves something demonstrable.

1. **Extension skeleton + Supervisor** — activate, spawn the room
   standalone, show its health, shut it down cleanly. Windows tree-kill
   included from the start, because retrofitting it is how strays happen.
2. **Orchestrator session + chat webview** — a working chat with a real
   Claude, no workers. Usable on its own.
3. **`orchestrator-bridge.mjs` + `POST /api/delegate`** — the orchestrator
   can delegate; results arrive as new turns.
4. **Workers panel** — spawn one OpenCode worker, render its activity and
   deadline.
5. **Installer + packaging** — detection, consented install, `.vsix`.

## Testing

The room's suite stays as it is and must stay green throughout.

The extension gets its own `node --test` suite over the pure parts, with
no VS Code API and no real binaries:

- the stream-json parser, fed recorded event fixtures (captured from the
  real binary during this design, so they are real shapes rather than
  invented ones)
- `Supervisor` state transitions with an injected spawn, including a child
  that exits immediately and one that never starts
- installer detection with injected `env`/`platform`/`exists`, reusing the
  `resolveCommand` approach that already covers Windows and POSIX from one
  machine

Anything requiring the VS Code host or a real binary stays a documented
manual check, recorded honestly in the README the way the OpenCode smoke
test already is.

## Risks

- **Process lifecycle on Windows** is the top risk and has already bitten
  twice. Tree-kill is a stage-1 requirement, not a polish item.
- **Ambient config collisions.** The orchestrator inherits user hooks and
  CLAUDE.md. A `SessionStart` hook injecting a large instruction block
  (observed on this machine) could work against the orchestrator prompt.
  Mitigation is prompt robustness, not isolation, since isolation costs
  the login.
- **Free-model reliability.** Unchanged from the OpenCode work, but more
  visible in a GUI. The deadline countdown is the mitigation.
- **VS Code API surface** is new to this repo. Keeping all logic in pure,
  injectable modules and the API usage thin is what keeps it testable.
